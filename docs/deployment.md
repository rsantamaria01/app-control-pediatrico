# Deployment runbook

Deploy one Compose project and one database per clinic. TLS termination and the public HTTPS origin belong to the external reverse proxy; the app listens on port 3000. Restrict direct access to port 3000 and configure the proxy to overwrite forwarded headers. Do not put credentials or bootstrap links in source control, shell history, tickets or shared logs.

## Configuration

Create a local, git-ignored `.env` from `.env.example` and set unique production values before starting. Compose uses `DB_PASSWORD` for PostgreSQL and the app/ops database connection, and `S3_ACCESS_KEY` and `S3_SECRET_KEY` for RustFS and the app. Set `NUXT_APP_SECRET` (stable, random, at least 32 characters), `RECOVERY_QUEUE_SECRET` (stable 32 random bytes in hex), and `NUXT_PUBLIC_SITE_URL` (externally reachable HTTPS origin). Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_SECURE`, and, for authenticated SMTP, both `SMTP_USER` and `SMTP_PASS`. Set `AUTH_TRUSTED_PROXY_CIDR` only for a proxy that overwrites forwarded headers and blocks direct access. Optional branding uses `NUXT_PUBLIC_CLINIC_PRIMARY` and `NUXT_PUBLIC_CLINIC_LOGO`. Do not use example passwords in a public deployment.

Compose passes the raw `DB_PASSWORD` with fixed `DB_HOST=db` and `DB_NAME=pediatrico` to the app and ops; the Node entrypoint percent-encodes the password into `DATABASE_URL` for each child and removes the raw variable from the child environment. Do not assemble `DATABASE_URL` by string interpolation or override it in `.env`; delimiters in passwords must remain valid. The app gets `REDIS_URL` and S3 connection details; ops gets the same database password and the `.env` values needed for bootstrap. Avoid changing `DB_PASSWORD` without also updating the PostgreSQL user's password in the existing volume. Pin and review the RustFS image version before production use.

## First deployment

1. Provision a clinic-specific host, external TLS proxy, DNS, secure local `.env` and backup destination; verify the proxy and outbound SMTP configuration.
2. Run `docker compose --profile full up -d --build`. The `ops` container waits for a healthy database, runs committed Drizzle migrations, and exits successfully before the `app` starts. If migration fails, the app must not start: inspect `docker compose --profile full logs ops`, fix the cause and retry. Do not bypass the migration gate.
3. Set `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_EMAIL` temporarily in the git-ignored `.env` (restrict its permissions). Run `docker compose run --rm ops bootstrap-admin`. The command requires the HTTPS site URL and an empty user table with no prior bootstrap marker; it prints one single-use, seven-day invitation link. Deliver it privately to the administrator, set a password via the link, then remove the temporary bootstrap variables. Do not rerun bootstrap after users exist.
4. Verify sign-in, invitation email delivery, application logs, and the protected clinical access path with a real authorized account.

## Upgrades and recovery

### Upgrade with a write-free window

Schedule maintenance and block all external writes at the proxy (including direct port 3000 access), then wait for in-flight requests to drain. This is not sufficient for a backup: the app's recovery worker can write to PostgreSQL without an HTTP request. Prepare an empty, private, local backup directory on the Docker host (owned by the operator, mode 0700; replace `RELEASE-ID` with a unique identifier). The script never overwrites a dump and uses a restrictive umask; verify sufficient free disk space first. Arrange an independently verified RustFS snapshot/export procedure and destination **before** starting the upgrade. In the project directory run:

```sh
BACKUP_DIR=/secure/backup/clinic-RELEASE-ID sh scripts/upgrade.sh
```

The script builds both new images first, stops the old `app` (including its recovery worker), checks `docker compose --profile full ps --status running -q app` is empty, then streams a custom-format PostgreSQL dump from `docker compose --profile full exec -T db pg_dump -U pediatrico -d pediatrico -Fc` directly into `$BACKUP_DIR/clinic.dump` on the host. No database port is published. It refuses to overwrite a prior dump and checks the archive with `pg_restore --list` before asking for operator confirmation. **While the app remains stopped**, take a paired RustFS snapshot/export of `storage-data` using the storage vendor's verified procedure; record the snapshot identifier, checksum, exact app version and dump checksum together off-host. Type `snapshot-verified` only after verifying the snapshot and backup location. The script then runs `ops db:migrate` and starts the full profile. Do not start any other app, ops, worker or writer until both backups are complete. A failed build, stop, dump, archive validation, missing confirmation or migration exits before app startup; keep the proxy in maintenance mode and investigate `docker compose --profile full logs ops` and the one-shot command output. `service_completed_successfully` also gates app startup; **it does not stop an already-running app**. Run the script only as the single deployment operator, not concurrently with other `docker compose up` commands or other writers. Do not use `docker compose --profile full up -d --build` for upgrades while the old app serves traffic. Keep maintenance active until the new app and protected access checks pass; only then reopen writes. Do not run `bootstrap-admin` during upgrades. Restore a compatible backup before rolling back an incompatible schema. A missing-schema recovery worker logs `schema not migrated` once and retries with a five-second backoff; migration failure still requires operator action.

### Backup and isolated restore drill

The upgrade script's `docker compose exec -T db` stream backs up **all** PostgreSQL schemas and tables, including `drizzle.__drizzle_migrations` and auth tables, without a host database port or password argument. For a standalone backup, first put the proxy in maintenance and stop the app/worker (`docker compose --profile full stop app`); verify `docker compose --profile full ps --status running -q app` returns nothing, then run `umask 077; docker compose --profile full exec -T db pg_dump -U pediatrico -d pediatrico -Fc > /secure/backup/clinic.dump` into a new protected destination, check it is nonempty, validate it with `docker compose --profile full exec -T db pg_restore --list < /secure/backup/clinic.dump > /dev/null`, and snapshot RustFS while the app remains stopped. This only validates the archive structure; a restore drill is still required. Use `sha256sum /secure/backup/clinic.dump` to record its checksum and compare it after transfer. Do not resume writes between the PostgreSQL dump and RustFS snapshot. The RustFS snapshot/export and restore are **manual gates**: this project has not pinned a vendor version or verified vendor-specific commands, so do not claim the paired backup is usable until the vendor procedure has been run and checked against the exact deployed RustFS version. Preserve its configuration and encryption keys. Encrypt the paired backup before off-host transfer; restrict access and retention. Valkey (`cache-data`) is ephemeral cache/rate-limit state, not a database or object-storage backup.

Test a restore only on a **separate isolated host and Compose project** with its own volumes, credentials and proxy disabled; never connect this drill to live volumes, networks or the live clinic. Start only the isolated `db` service (`docker compose up -d db` in that project's directory). Decrypt a copy of the archive to a protected local file on the isolated host; do not put credentials in command arguments or logs. Verify the Compose project and its database volume are isolated, then create a test database and stream the archive into the container without publishing a database port:

```sh
docker compose exec -T db createdb -U pediatrico -T template0 pediatrico_restore_test
docker compose exec -T db pg_restore -U pediatrico --no-owner --no-acl --exit-on-error -d pediatrico_restore_test < /secure/backup/clinic.dump
docker compose exec -T db psql -U pediatrico -d pediatrico_restore_test -X -c 'SELECT count(*) FROM drizzle.__drizzle_migrations;'
docker compose exec -T db psql -U pediatrico -d pediatrico_restore_test -X -c 'SELECT count(*) FROM "user";'
```

The isolated role must have CREATEDB and schema-creation permission; never grant extra privileges to the live app role to facilitate a test. Confirm migration count, user count and representative clinical records against backup metadata. **Manual RustFS restore gate:** on the isolated host, restore the paired RustFS snapshot to **isolated** storage using the documented procedure verified for the pinned vendor version; verify object count/checksums and read a representative authorized record and object with test access controls, without emailing real users. Do not call the drill complete or reopen a restored clinic without validating both stores together. Destroy the isolated project and plaintext dump securely afterward. A real incident restore requires a separately reviewed maintenance plan, confirmed backup compatibility and explicit target verification; never run these commands against live production.
